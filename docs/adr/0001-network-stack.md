# ADR 0001: Сетевой стек (синхронизация клиентов)

## Статус

Принято (документация v1).

## Контекст

Нужна двусторонняя синхронизация состояния для: лобби, выбора персонажей, **поэтапного** ретро, движения и боя на арене, голосований. Транспорт реального времени — **WebSocket**; **HTTP** (REST/JSON) — для bootstrap (создание сессии, ключ) и прочих запросов по необходимости.

## Решение

- **WebSocket** с **авторитетным сервером**: сервер рассылает обновления всем участникам комнаты; клиенты не считаются доверенными для фаз и итогов голосований.
- **REST/JSON** — создание сессии, валидация ключа, метаданные по мере роста API.

## Обоснование

- Фазы ретро **последовательны** и управляются **ведущим** — одна «комната» на сервере с явной машиной состояний.
- **WebSocket** даёт низкую задержку для событий комнаты и дуплекс без поллинга; нагрузка управляется размером сообщений и **rate limits** на уровне сервера.

## Последствия

- Реализовать **комнаты** и **серверную машину состояний** фаз.
- Клиент устанавливает WS после входа в сессию; переподключение — отдельная спецификация протокола.

## Отклонённые варианты (кратко)

- **Только REST + long polling** — проще, но хуже для движения/боя и частых обновлений.
- **SSE** — односторонний поток с сервера; для ввода игрока не подходит как единственный канал (нужен второй канал или WS).
