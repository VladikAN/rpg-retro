# ADR 0003: Клиентский рендер — Phaser 3

## Статус

Принято.

## Контекст

Нужен 2D-рендер в духе [REQUIREMENTS.md](../REQUIREMENTS.md) (тайлы/спрайты 32×32, дальше — движение, бой). Клиент — **TypeScript**, репозиторий — **монорепо** с `server/` (Go) и `client/`.

## Решение

- Игровой клиент строится на **Phaser 3** (текущая ветвь 3.x).
- **Сборка** — **Vite** + TypeScript, строгий режим TS ([`.cursor/rules/typescript.mdc`](../../.cursor/rules/typescript.mdc)).

## Обоснование

- Встроенные **сцены** (Scene): удобно разделить **арену** (игровой холст) и вспомогательные экраны.
- Работа со **спрайтами, тайлмапами, анимациями** — без низкоуровневого кода с нуля; соответствует дорожной карте (арена, потом сущности).
- Зрелая экосистема, документация, примеры для **мобильных** viewport.

## Риски и смягчение

- **Размер бандла** Phaser выше, чем у «голого» Canvas/WebGL ([NFR.md](../NFR.md)):  
  - **code splitting** / **динамический import** Phaser **только** на маршруте, где открывается игра/арена (если стартовая **лендинг-страница** без Phaser — быстрее первая отрисовка).  
  - Следить за **production**-сборкой (minify, при необходимости manual chunks).
- Привязка к API движка: обновлять Phaser **осознанно** (changelog).

## Монорепо

- `client/` — отдельный проект (npm), зависимости Phaser; **не** смешивать go.mod с npm в одном «корне пакетов» — два независимых манифеста в одном git-репо.

## Последствия

- Документация и тикеты по UI арены формулировать в терминах **сцен Phaser** там, где это уместно; сетевой слой — отдельный модуль, вызываемый сценой.
