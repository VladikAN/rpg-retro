# Архитектура и стек (черновик)

## 1. Цель документа

Зафиксировать **разумный по умолчанию** стек и **альтернативы** — без догмы. Финальные выборы обновлять по мере прототипа.

## 2. Клиент

- **Язык:** **TypeScript** (строгий режим по мере введения `tsconfig`).
- **2D / «минимальный движок»:** варианты, хорошо сочетающиеся с браузером и 32×32:
  - **Phaser 3** — зрелый 2D, встроенные сцены, пулы, тайлмапы; **рекомендуемая отправная точка** для бродилки + простых врагов.
  - **PixiJS** — низкоуровневый рендер; больше ручного кода (сцена, ввод, коллизии) — смысл, если нужен минимальный вес.
  - **Кастом на Canvas 2D** — максимальная лёгкость, **максимум** ручной работы.

*Рекомендация агента: начать с **Phaser 3** + **Vite** для дев-сервера и бандла.*

## 3. Сервер: ответственность (общее)

На сервере, каким бы ни был стек, логично держать вместе:

- **CRUD** и жизненный цикл **групп/сессий** (создать, получить по коду, завершить, владелец, текущий ведущий).
- **Раздача фронтенда:** после сборки `apps/client` — статика (например `index.html` + `assets/`), **один** entrypoint в проде (удобно в **Go** через `embed`, либо контейнер с `nginx` — TBD).
- **Real-time:** **WebSocket** для авторитетного **game state** (позиции, этапы ретро, карточки) — типично для MVP и e2e. Параллельно (или вместо части трафика) **WebRTC**: сервер **не** «создаёт магию VPN», а **оркестрирует** соединения: **сигнальный** обмен SDP/ICE, при необходимости выдача **TURN** из **env** (и STUN-URL). Для P2P game state нужна явная **модель** (клиент-хост, merge-стратегия) — согласовать в дизайне, см. `docs/CJM.md`, `docs/E2E.md`.
- **Доступ в комнату:** **знание ключа** приглашения, без личного аккаунта по умолчанию (см. `docs/REQUIREMENTS.md`).

### 3.1. Вариант: Go (рекомендовано рассматривать)

**Почему Go подходит под ваше описание (CRUD групп, статика игры, сигнальный слой WebRTC):**

- Один **статический бинарь** + встраивание `dist` клиента через `embed` — **простой** образ **Docker** и **один** процесс в `docker-compose`.
- `net/http` и лёгкий **роутер** (chi, Echo, Fiber — выбор на реализацию) для **REST** (сессии, health) и **спа-фолбэка** `GET *` → `index.html` для Vite-роутинга, если появится.
- **WebSocket** (часто **gorilla/websocket**) для **синхронного** состояния; отдельные **HTTP- или WS-маршруты** для **сигналинга** WebRTC (JSON с типами: offer, answer, ice-candidate).
- **Pion (webrtc):** **опционально** (SFU, запись, проверка SDP). Для **чистого** relay offer/answer/ICE **достаточно** HTTP+JSON **или** отдельного **WebSocket-канала**; объединение pion и ws **в** **одном** **процессе** **—** **на** **усмотрение** **команды.**
- **MVP (одна строка):** Go + REST (CRUD) + раздача статики + один транспорт состояния (чаще WebSocket) + сигналы WebRTC; e2e (Playwright) против той же сборки в CI — `docs/E2E.md`.

**Инструменты:** pion, gorilla/websocket, при появлении **БД** — `migrate` или **sqlc** (TBD).

### 3.2. Альтернатива: Node.js

- Тот **же** набор функций: **Express/Fastify** (или **Nest** — TBD) + **REST** + **static** (или Vite **только** в **dev**).
- **Плюс:** та же экосистема, что и у клиента (TypeScript), много готовых кирпичей.
- **Минус:** релизный «бинарь + вшитый клиент» с Node собрать труднее, чем с Go+embed; для жёсткой «одна команда, один образ» Go зачастую проще.

### 3.3. WebRTC: уточнение терминов

- **«Сервер раздаёт WebRTC»** в бытовом смысле = **сигнальный** обмен (SDP, ICE) + при необходимости **TURN** из **env** (и **STUN**-URL). Плюс отдельно решается, **где** хранить **авторитетное** game state: чаще всё ещё **на сервере** (тот же процесс, чаще через **WebSocket**), а P2P — **дополнительный** канал по необходимости.
- Не путать **успех сигнального обмена** (peer connection открыт) и **согласованность** карточек, этапов ретро и ведущего. Для **CJM-4** вторая часть обычно опирается на **тот же** бэкенд, что и CJM-1–3, если только вы **осознанно** не вынесли state в P2P с **явной** **моделью** (см. `docs/CJM.md`).

## 4. Схема данных (логически, без схемы БД)

- **Сессия (room):** `inviteKey`, `leaderId` / `facilitatorId`, список `players[]`, `stage` (enum ретро), `cards[]`, `votes`, опционально `locationId`.
- **Сообщения:** JSON с полем `type` и `payload` (версионировать при эволюции API).

*Хранение: в памяти процесса — для MVP/нагрузочных тестов; **Redis/Postgres** — при необходимости персистентности и рестартов — вынести в отдельное решение.*

## 5. Сборка и репозиторий (монорепо — согласовано)

- **Monorepo:** **разделение** по папкам:
  - **`apps/client/`** — браузерный клиент (2D, UI ретро);
  - **`apps/server/`** — бэкенд (предпочтительно **Go:** REST, WebSocket, сигналы WebRTC, при необходимости **Pion**); **Node** — допустимая альтернатива, см. §3.2.
- **Менеджер пакетов** и **workspaces** (`pnpm` / npm) — **зафиксировать** при инициализации `package.json` в `apps/*` (корневой workspace — TBD).
- **Линт / формат:** **ESLint** + **Prettier** — детали в `docs/CODE_STYLE.md` при подключении.
