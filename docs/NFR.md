# Нефункциональные требования

## 1. Платформы и UX

- **Целевые устройства:** современные браузеры на **ноутбуках** и **мобильных** телефонах.
- **Viewport:** адаптивный UI; сенсорное управление на мобилках (тапы, отсутствие hover-only критичных действий).
- **Доступность:** крупные кликабельные зоны где возможно; контраст — не ниже разумного минимума для читаемости на слабых экранах (итеративно).

## 2. Сеть

- **Транспорт** — по [ADR 0001](adr/0001-network-stack.md): **WebSocket** и авторитетный сервер; задержка терпима для пошаговых фаз ретро, не для киберспорта.
- **Переподключение:** зафиксировать в реализации (восстановление сессии в комнате по токену/сессии — на этапе проектирования API).

## 3. Масштаб

- **Размер одной сессии** — ожидаемо малый/средний командный ретро (порядок **2–20** участников; точный лимит — решение при нагрузочном/продуктовом уточнении).
- **Нагрузка** — низко-средняя; не требуется MMO-уровень.

## 4. Безопасность и конфиденциальность

- **Секреты** не хранятся в репозитории; только переменные окружения (см. `.env.example`).
- **По умолчанию** не логировать содержимое карточек и персональные идентификаторы в неочищенном виде; уровни логирования — по политике деплоя.
- **Голосования** с пометкой «анонимно» — сервер и клиент не должны **раскрывать** голоса другим участникам в UI (только агрегат по итогу, если так задумано в продукте).

## 5. Развёртывание

- **docker-compose** для локального/демо-рана.
- **Конфигурация** — через env; без hardcoded production URL/паролей.

## 6. Сопровождаемость

- E2E на критичных путях — [E2E.md](E2E.md).
- ADR при смене значимых архитектурных решений — [docs/adr/](adr/).

## 7. Производительность (клиент)

- Клиент — **Phaser 3** ([ADR 0003](adr/0003-client-rendering-phaser.md)); **бандл** держать в разумных пределах для мобильного LTE: production-сборка, по возможности **отложенная загрузка** Phaser **только** для экрана, где он нужен (арена, не лендинг).
