# Требования

## 1. Функциональные

### 1.1 Сессия и доступ

- Пользователь открывает игру по **ссылке**.
- Подключение к **группе (сессии)** по **ключу приглашения**; ключ может быть **в URL** (query/fragment) или введён вручную.
- **Сервер** определяет группу и **добавляет** игрока в сессию.
- **Создатель группы** — **главный** (facilitator по умолчанию): выдаёт ключ, может **вести ретро** или **назначить** другого ведущего.
- **Создатель** определяет **сценарий** сессии (шуточный нарратив): **локация**, **объект** сбора карточек (кубок, сундук и т.д.), **шаблон** текста финального голосования. Подробно — `docs/GAME_DESIGN.md` (раздел «Сценарий (задаёт создатель)»). **Когда** выбирать сценарий в UI (при создании / в лобби) — TBD.

### 1.2 Персонажи

- Каждый игрок **выбирает одного** из заранее заданных персонажей (пример: рыцарь, маг, скелет, разведчик).
- У каждого персонажа **одна** активная **способность/атака** (фаербол, меч, лук и т.д. — детализация в `docs/GAME_DESIGN.md`).

### 1.3 Ретро: этапы (управление ведущим)

Ведущий **переключает этапы** ретро через UI. Поддерживаемые **категории этапов** (формулировки могут уточняться в дизайне):

1. Сбор **положительных** карточек.
2. **Вскрытие** всех карточек (до вскрытия — **анонимно**; см. `docs/GAME_DESIGN.md`).
3. **Поочерёдная презентация** каждой карточки.
4. Сбор **негативных** карточек.
5. Снова **вскрытие** карточек.
6. **Голосование** за карточки (для **приоритизации** в середине сессии).
7. **Разбор** карточек и **экшен-план** по каждой / выбранным.
8. **Итоговое анонимное голосование сценария** (последний этап): вопрос в духе «удалось ли команде завершить сценарий» (текст из сценария, шуточно). **ЗА** — доволен ходом ретро и экшен-айтемами; **ПРОТИВ** — не рад, как прошло ретро / итогу. **Не** связывать с золотом и с **п. 6** (приоритет карточек). Подробно — `docs/GAME_DESIGN.md`, раздел «Итоговое голосование сценария».

- Поведение на этапах **согласуется** с **визуалом** **и** **сценарием**; **объекты** сбора и **текст** финала — из **сценария** (§1.1, `docs/GAME_DESIGN.md`).

### 1.4 Сбор карточек (асинхронно, игровое действие)

- Во время этапов **сбора** положительных/негативных карточек ввод **асинхронный** (не обязан быть «по одному пишущему»).
- Чтобы открыть ввод, игрок **должен совершить действие в мире**: подойти к **объекту сбора, заданному сценарием** (кубок, сундук, стол и т.д.) и **использовать** действие взаимодействия (например «удар» / «постучать») — в ответ открывается **стилизованное окно** ввода.
- Содержимое окна (минимум): поле **текста** карточки, действие **добавить карточку**, **показать свою предыдущую** (для **редактирования**), **отправить** карточки (сохранить/зафиксировать на стороне сессии).
- **Какой** объект на сцене **задаёт** **сценарий**; см. `docs/GAME_DESIGN.md`.

### 1.5 Параллельный геймплей (арена)

- Этапы **не обязаны** «блокировать» свободу передвижения: игрок может **ходить** по **небольшой локации** и участвовать в **сторонних активностях**.
- **Простые враги** (крысы, летучие мыши, скелеты); победа — **выброс добычи** (золото — **только косметика/шутка**, на ход ретро **не** влияет; итоговый экран может показать **«самого богатого»**). Подробнее — `docs/GAME_DESIGN.md`.

### 1.6 Локации (контент)

- Каталог карт/фонов (тронный зал, казармы, пещера и т.д.) **связывается** с **сценарием** (§1.1, `docs/GAME_DESIGN.md`). **В** MVP **достаточно** **одной** **согласованной** **тройки: локация** + **объект** сбора + **текст** **финального** **вопроса.**

## 2. Нефункциональные

| Область | Требование |
|--------|------------|
| **Клиент** | Современные браузеры; **адаптивная** вёрстка/управление под **touch** и **desktop**. |
| **Сеть** | Низкая задержка **желательна**; устойчивость к кратким обрывам (желательно: переподключение, явные состояния «отвалился / вернулся» — уточнить в реализации). |
| **Безопасность** | Секреты только через **env**; не хранить в репозитории. |
| **Сборка и деплой** | **docker-compose**; конфигурация из переменных окружения. |
| **Производительность** | Целевые устройства: ноутбуки и телефоны; 2D, ограниченный спрайт-арт **32×32** — см. `docs/GAME_DESIGN.md`. |
| **Сессия** | **Ориентир** — до **~16** игроков; **большее** число участников **не** обязательно **жёстко блокировать** (инженерно — нагрузка и UX уточняются в реализации). |
| **Масштаб** | «Небольшая» игра — **не** заявлять MMO-уровень. |

## 3. Вне объёма (на текущий момент)

- Встроенный голос/видео/чат (используется внешний софт).
- Полноценный продакшн-аккаунтинг, биллинг, модерация контента (кроме минимальной защиты от злоупотребления сессиями — TBD).

---

## 4. Критерии готовности MVP (черновик)

MVP будет уточняться; ориентиры:

- [ ] Создание сессии, ключ, вход по ссылке/ключу.
- [ ] Выбор персонажа, синхронное присутствие в «комнате».
- [ ] Один **полный цикл** этапов ретро с **управлением ведущим** (хотя бы в упрощённом UI).
- [ ] Одна **арена** с передвижением, одним типом врага и **дропом** золота.
- [ ] **Docker-compose** для локального/стендового запуска без секретов в репо.

*Детализация критериев — по согласованию, после уточнения приоритетов.*
