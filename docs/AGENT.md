# Память и контекст агента

Документ для переноса контекста между сессиями и агентами. Обновлять по согласованию с владельцем проекта.

## Название и цель

- **Репозиторий / продукт:** `rpg-retro` (рабочее имя) — лёгкая **браузерная** игра для **командных ретро** (юмор, низкий порог входа).
- **Платформы:** любой браузер с интернетом; **приоритет UX:** ноутбуки и мобильные телефоны.
- **Внешняя коммуникация** (Zoom, Discord и т.д.) **вне** объёма проекта; в игре — только игровой опыт и синхронизация состояния.

## Ключевые договорённости

1. **Тикеты (issues):** на старте **не** ведём; позже — только **с согласованием** (создание, пересмотр, закрытие). Когда появится GitLab — зафиксировать workflow в `docs/PROCESS.md`.
2. **Секреты:** никаких ключей/паролей в коде; только **переменные окружения** и примеры в `.env.example`.
3. **Деплой:** целевой способ — **docker-compose**; детали — `docs/DEPLOYMENT.md`.
4. **Стек:** ориентир в ТЗ — **JS/TS**, минимальный **2D-движок**, сеть — **WebSockets и/или WebRTC**; окончательные решения — в `docs/ARCHITECTURE.md` (с обоснованием и альтернативами).

## Открытые вопросы (актуализировать)

- Лицензия и публикация ассетов (если будут чужие спрайты).
- Нужен ли **зрительский** режим без ключа (только наблюдатель) — в ТЗ не требуется.
- Минимальное и максимальное число игроков в сессии.
- Требуется ли **аудио/чат** внутри игры в будущих фазах — сейчас вне scope.

## История смысловых решений (кратко)

- **WebRTC vs WebSockets:** для синхронизации **состояния игры** (позиции, этапы ретро, карточки) обычно проще и предсказуемее **WebSocket + авторитетный сервер**. WebRTC (DataChannel) — кандидат, если цель — снизить нагрузку на сервер **и** согласны с усложнением (NAT, хост, при необходимости TURN). Подробнее — `docs/ARCHITECTURE.md`.
- **Визуал:** ориентир *Vampire Survivors* — простая спрайтовая 2D, **32×32** тайлы/база персонажей, анимация через кадры спрайта и/или простой твин (подпрыгивание/сдвиг).
