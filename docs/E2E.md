# E2E-тесты и связь с CJM

## Зачем

- **E2E** (сквозные браузерные тесты) проверяют **собранный** продукт: **клиент** + **сервер** + **реальный** HTTP/WebSocket (и при внедрении — **сигнальный** слой **WebRTC**), как у пользователя.
- Цель по процессу: **на каждом значимом этапе разработки** прогонять e2e, чтобы **подтверждать** работоспособность **всей цепочки**, а не только единичного модуля.

*Unit / интеграционные тесты* дополняют e2e, но **не** заменяют сценарии из `docs/CJM.md`.

## Рекомендуемый инструмент

- **Playwright** (TypeScript) — **один** репо с `apps/client`, стабильные селекторы, headless/CI, trace при падении.
- **Запуск:** `docker compose up` (или `docker compose -f ...`) + **база URL** из **`PLAYWRIGHT_BASE_URL`** / `.env` (см. `.env.example` при появлении e2e).

*Альтернатива:* Cypress — допустим, но в одном стеке с Vite/TS **Playwright** чаще проще для CI и мульти-страничных / multi-tab (два «браузера» = два участника — см. ниже). **Selenium** — не выбирать без веской причины (тяжелее, хуже DX).*

## Привязка к CJM (карта тестов)

Минимальный **набор**, который **регрессирует** продукт, когда меняется что угодно (клиент, сервер, **Go**-бинарь, **nginx**-прокладка).

| CJM  | E2E (идея) | Ключевые проверки |
|------|------------|--------------------|
| CJM-1 | `e2e: create-session` (имя — условно) | GET `/` → **«Создать»** → в ответе/на экране **есть код/ссылка**; `POST` на API (если отдельно) **201**; **сессия** в API списка (при **CRUD**-debug). |
| CJM-2 | `e2e: join-lobby` | Второй контекст/страница: ввод кода+имя → **лобби**; **список** видит **оба** (или **ожидания** `expect.poll` по **WS**-снапу — как реализуете). |
| CJM-3 | `e2e: start-arena` | **Готов** / **Начать** → **экран арены**; **персонаж** выбран, **тайл-локация** виден (скрин или data-testid). |
| CJM-4 | `e2e: retro-happy-minimum` | Ведущий: **смена этапа**; участник: **к столу** (или **mock**-упрощение UI — **только** с флагом dev) → **текст карточки** **отправлен**; опционально **2-й** участник видит **вскрытие** после **этапа ведущего**; **враг** = удар → **+золото** (если в e2e есть спавн). |
| CJM-5 | `e2e: end-session` | **Завершить** → **экран итогов** / редирект; при наличии **«самого богатого»** — **assert** по **data-testid**. |

**Стабильность:** `data-testid` на **кнопки** (создать, войти, начать, следующий этап), на **код** сессии, на **счётчик** золота, на **текст** в лобби.

**Два пользователя в одном тесте:** Playwright **browser.newContext()** x2 (или `page1`, `page2`).

## Когда гонять

- **CI:** на `merge` в `main` и/или **каждый** MR, если e2e **< ~10** мин. и окружение готовит **docker** job.
- **Локально:** перед крупным **релизом** и **при изменении** сервера (особенно **сигнальный** **WebRTC**, **маршруты** статики).

## Что **не** гоняем e2e без необходимости

- **Чистую** **WebRTC** **медиа**-качество (TURN, firewall) — это **ручной** / **staged** прогон; e2e проверяет **сигнальный** happy-path (offer/answer обменялись, `connectionState` **connected** / **таймаут**-skip в CI, если flacky).

*Детали e2e для WebRTC уточнять после **реализации** `pion`/`adapter` / маршрутов; до тех пор — **заглушка** тест: «**сокет/HTTP**-сигнальный маршрут** отвечает**».*

## Каталог в репо (когда появятся тесты)

- Рекомендуемая раскладка: **`e2e/`** в **корне** (`e2e/tests/*.spec.ts`, `e2e/playwright.config.ts`), **не** в `apps/client`, чтобы e2e **смотрел** на **собранный** `dist` и **go**-сервер, как в проде.

*До первого кода: достаточно **этого** `docs/E2E.md`.*

## Связь с **навыками** и **ролями**

- **Тестировщик** (см. `docs/ROLES_AND_SKILLS.md`) **поддерживает** e2e **в актуальном** виде **относительно** `CJM` и **чек-листов** покрытия.
- **Ревьюер** **не** мерджит без **зелёного** e2e в **CI** (когда e2e подключен), если **не** **явное** `skip` + **тикет**-долг.
