# CJM: основные сценарии

Цель: **почти линейные** пути **без лишних ветвлений** — в реальном продукте добавляются ошибки сети, валидации, выходы; их обрабатываем в **требованиях** и **e2e** отдельно, в CJM не расписываем.

**Термины:** **организатор** — кто создал сессию и (по умолчанию) **ведущий**; **участник** — вошёл по коду. **Сервер** = веб-интерфейс (лендинг/лобби/создание) + API + раздача клиента; см. `docs/ARCHITECTURE.md`.

---

## CJM-1. Организатор создаёт ретро и получает код

1. Пользователь открывает **URL** приложения (тот же хост, что и сервер).
2. Видит **веб-интерфейс** (стартовый экран).
3. Нажимает **«Создать ретро»** (или эквивалент).
4. Система создаёт **сессию (группу)** на сервере и показывает **код приглашения** (и готовую **ссылку с кодом** — удобно копировать).
5. Организатор **передаёт** код/ссылку **участникам** (мессенджер, устно — вне продукта).

*Дальше участники подключаются; организатор остаётся в **лобби** до готовности или сразу назначает ведущего (если вынесем в сценарий CJM-3 — сейчас: по умолчанию организатор = ведущий, см. CJM-4).*

---

## CJM-2. Участник входит по коду, имя, ожидание в лобби

1. Участник открывает **URL** (тот же) или **ссылку** с **уже подставленным** кодом.
2. Вводит **код** (если не в ссылке) и **имя** (отображаемый ник).
3. Подтверждает вход **«Войти»** / **«К команде»**.
4. Попадает в **лобби** сессии: видит **список** подключившихся, ожидает, пока все готовы (или сигнал от ведущего).

*Минимальные ответвления, не входящие в «основной» CJM, но важны для e2e: неверный код, дубликат имени, переподключение — `docs/REQUIREMENTS.md` + `docs/E2E.md`.*

---

## CJM-3. Старт: персонаж, арена

1. В **лобби** все отмечены «готовы» (кнопка) **или** ведущий нажимает **«Начать»** (один путь в продукте — зафиксировать в реализации, не раздваивать CJM).
2. Каждый **выбирает персонажа** (один на игрока).
3. Система **переходит** на **локацию (арену)**: ведущий **на позиции** (трон / дракон), участники **на спавнах**; **этап ретро** — начальный (например, сбор плюсов — как в `docs/GAME_DESIGN.md`).

---

## CJM-4. Ретро на арене (ведущий ведёт этапы, участники играют)

1. **Ведущий** через **панель** **переключает этапы** ретро (по порядку из `docs/GAME_DESIGN.md` / `docs/REQUIREMENTS.md`).
2. **Сбор карточек (позитив/негатив):** участник **подходит** к **столу/кубку** → **действие** (взаимодействие) → **окно** ввода → **сохранить/отправить**; **анонимно до вскрытия** — как в соглашениях.
3. **Вскрытие / презентация / голосование / разбор** — **визуал** (карточки, увеличение, и т.д.) + синхронизация; ведущий **ведёт** порядок, где требуется.
4. Параллельно участники **свободно ходят** и **долбят** простых **врагов**; **золото** с врагов **косметическое** (см. дизайн); на **рост приоритета** ретро **не** влияет.

*Одна ветвь, которую стоит заранее согласовать: **«назначить другого ведущего»** — либо отдельный CJM-5, либо внутри CJM-4 как **один** клик без подсценов.*

---

## CJM-5. Завершение

1. **Ведущий** (или **организатор** — как решите) завершает **финальный** этап (разбор/план) и нажимает **«Завершить сессию»** / **«Покинуть сессию»**.
2. **Экран итогов** (минимум): **опционально** **«самый богатый»**; список карточек/экшен **TBD** по глубине MVP.
3. Участник может **выйти** / **открыть новую** ссылку (новая сессия — CJM-1 снова).

---

## Сводка: зависимость e2e

| ID     | Сценарий |
|--------|----------|
| CJM-1  | Создать сессию, увидеть код/ссылку |
| CJM-2  | Войти по коду, имя, лобби |
| CJM-3  | Готовность → персонажи → арена |
| CJM-4  | Этапы ведущего, минимум одна карточка через стол, одна смена этапа, при желании **дым** врага |
| CJM-5  | Завершение, экран с «богатством» (если в MVP) |

Покрытие: `docs/E2E.md`.
